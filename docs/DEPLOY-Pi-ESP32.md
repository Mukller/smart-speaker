# Перенос на Raspberry Pi и ESP32

Колонка сейчас работает как веб-приложение: звук, микрофон и будильник
исполняет браузер, а сервер только считает. Это сделано потому, что в
контейнере на сервере нет ни звуковой карты, ни `aplay`. `GET /kolonka/api/audioHealth`
отвечает, что именно так и есть, и не даёт поверить, что звук «работает».

Проверять состояние перед любыми догадками:

```bash
curl -s https://antonpetnitsky.com/kolonka/api/audioHealth | python3 -m json.tool
```

## Raspberry Pi

Pi — это тот же сервер, только со звуком. Приложение уже умеет играть
локально: в репозитории есть четыре движка `plugin_playwav_*`, и выбором
занимается одна опция `playWavEngineId` в `options/core.json`.

Деплой выбирает её сам: если в контейнере есть `/dev/snd` и `aplay`, ставится
`aplay`, иначе `consolewav` и звук продолжает играть браузер. Проверяется
именно контейнер, а не хост, потому что конфиг читает ядро внутри.

Чтобы проверить это до переноса, на хосте с картой:

```bash
AUDIO_BACKEND=aplay bash deploy/deploy.sh
```

### Что уже проверено

- WAV, который отдаёт `/tts`, это `pcm_s16le`, 22050 Гц, моно, 16 бит.
  Ровно эти параметры ждёт `aplay -f S16_LE -c 1 -r 22050`, поэтому синтез
  играется без перекодировки, а `audioHealth` отдаёт готовые аргументы.
- На сервере есть `aplay`, `arecord` и `ffmpeg`, так что конвертация локальных
  треков для ПК в mp3 предложена верно.

### Что нужно сделать на Pi

1. Карта: USB-звуковая или HAT. Без неё останется браузер.
2. В контейнер: `apk add alsa-utils` (или apt) и `--device /dev/snd`,
   плюс группа `audio` для пользователя контейнера.
3. Микрофон для распознавания: контейнеру нужен `/dev/snd` и для записи.
   Сейчас `arecord -l` на сервере отвечает «no soundcards found», то есть
   ввода нет вообще, поэтому весь STT идёт из браузера.
4. Модели уже приезжают в том `irene_models`, отдельно ничего качать не нужно.

### Честно о непроверенном

Локальное воспроизведение **не проверено на реальной карте**: на сервере её
нет. Формат файла и набор движков проверены, сам звук на Pi услышать пока
нельзя. Первый запуск на железе стоит начать с `/audioHealth` и одного
короткого ответа, а не с полной настройки.

## ESP32

Здесь важно не создать ожиданий: **этот стек на ESP32 не запустится**.
Нужен Python с FastAPI, torch для silero, onnxruntime для vosk-tts и около
300 МБ моделей. ESP32-S3 — микроконтроллер с 512 КБ ОЗУ, ему не под силу
ни интерпретатор, ни модель распознавания.

Разумная роль ESP32 — тонкий клиент у этой же колонки:

- постоянное слово активации (у ESPHome и Voice Assistant есть готовые
  модели openWakeWord и Porcupine),
- захват с I2S-микрофона и отправка потока на `/kolonka/api/stt`,
- воспроизведение ответа на I2S-динамик.

То есть считает сервер, а железо работает как микрофон и колонка. Так
Pi-вариант и ESP32-вариант обращаются к одному и тому же API, и стыковка
получается в одном месте — в `runva_webapi.py`.

Полностью автономный ESP32 без сервера тоже возможен, но это будет
другая программа с нуля: `openWakeWord` плюс TinyWakeWord или Porcupine
плюс модель распознавания, влезающая в несколько мегабайт. К этому проекту
такой код отношения не имеет.

## Общее

Горячие точки при переносе:

- `playWavEngineId` — единственный переключатель звука, следить за ним.
- `/audioHealth` — источник правды, не догадки.
- микрофон в контейнере: без `--device /dev/snd` запись невозможна, и это
  видно в ответе, а не в логах.
